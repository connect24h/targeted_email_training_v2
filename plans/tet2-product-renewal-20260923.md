## 1. 推奨する方向

TET2を「メール訓練の設定画面の集合」から、**訓練を計画し、結果を確かめ、教育につなげ、顧客へ説明する運用ワークスペース**へ変える。
抜本的に変えるのは画面の色ではなく、作業の単位・画面間のつながり・結果の説明方法である。

- 強化する独自性: 日本語シナリオの調整、顧客別の運用代行、判定根拠が追える結果、報告書納品。
- 埋める基本機能: 配信前チェック、統合された対象者選択、報告受付とフォロー、文脈に合ったHELP。
- 追わない機能: 当面のAI全自動送信、音声・ディープフェイク、巨大なLMS、個人ワースト順位の演出。
- 技術方針: PHP/Python/SQLiteと既存の安全な送信処理を活かす。全面React化やDB置換をGUI改善の前提にしない。

主利用者は「少人数で複数顧客を支援する運用担当者」、次に顧客企業の担当者、受講者とする。
これは既存計画の一人運用・顧客向け運用代行という前提を継承した暫定判断。顧客セルフサービス中心なら後述のSSO/MFA・権限設計を前倒しする。

### この計画の合格条件

1. 現行コードで確認した機能、文書上の配備記録、未確認の本番状態を区別する。
2. KnowBe4・セキュリオの公式ヘルプを直接参照し、機能の有無だけでなく操作と制限を比較する。
3. GUIの情報構造、主要画面、HELP、受講者体験を具体化する。
4. 優先順位、成果指標、依存関係、受入条件、検証、戻し方を示す。
5. 実装・本番変更をせず、承認対象を明示する。

### GUIで優先して直す問題

- サイドバーは17項目が主に機能別に並ぶ。「何を終わらせるか」より内部機能の理解が先に必要になる（`index.html`）。
- ダッシュボードは件数中心。「キャンペーン別 反応状況」という見出しに対し、実際のグラフ系列は対象者数である（`app.js:220`）。
- キャンペーン編集は大きなモーダルへ対象者・送信設定・最大100コンテンツを集約。既存の折りたたみ機能は残し、長い作業には専用ページを使う（`app.js:1384`）。
- 報告照合は「ログ管理」、不審メール解析は「不審メール」、推奨教育は「リスク」に分かれる。調査と次の操作をつなぐ必要がある。
- `navigate()` は表示切替で、URL履歴による画面復元は確認できない。HELP専用の導線も確認できない。画面共有、戻る操作、問い合わせ時の特定を改善する。
- リスク画面には説明がある一方、別レポートには「ワースト順」「防衛失敗者」が残る。支援対象・観測された行動へ語彙を揃える。

### 機能追加より先に扱う安全・仕様の問題

1. **テスト送信の意味が文書間で違う。** READMEは少量matrix方式と記載するが、現行 `PipelineRunner` と `pipeline_test_delivery_test.php` は全対象行をテスト宛先へ均等転送する仕様を固定している。さらに画面には「テスト宛先が空なら本番宛先」という説明が残るが、現行生成・launch処理は空宛先を拒否する。コードに合わせて誤説明を直し、既存の全件検証は維持する。新しい少量プレビューは別モードとして提案する。
2. **入力値の取り扱い。** 旧経路は`/training_log.php`と通常ログを共有する。追加指示により、顧客承認参照があるキャンペーンの新規生成HTTPSページだけが専用APIへ入力本文を送り、別テーブルで暗号化保存する。未承認時は行為のみ記録する。通常明細・CSV/XLSXには本文を載せず、復号APIはシステム管理者のみ。master修正だけでは既存生成物へ反映されないため、その移行と共用受信側の扱いは本番変更前に別途確認する。過去ログを独断で削除しない。
3. **集計の語彙。** 現行UIの注記ではビーコンは偽サイト側にあり、メール開封ではない。古いKPI文書の「開封率」をそのまま営業資料へ転載しない。
4. **不審メールの所見。** 現行の低スコアを「安全」とする説明は、無害の証明と混同され得る。判定不能・未確認と、担当者が根拠付きで確定した分類を分ける。

## 4. GUIの全体構造

### 4.1 ナビゲーションを仕事の単位へ整理する

```text
運用ホーム             今日の要対応／今月の予定／稼働上の警告
訓練                    単発・定期一覧／キャンペーン詳細／作成
教育                    配信と進捗／教材・設問／学習プログラム
報告受付                訓練報告／不審メール／未照合・要確認
対象者・組織            人物／グループ／条件セット／取込
成果・レポート          訓練・教育・支援優先度／顧客報告／確定履歴
設定                    管理アカウント／送信環境／通知／監査／テナント
HELP                    この画面の使い方／初回設定／用語／問題の解決
```

「役職マスタ」「マスタ管理」「対象者集計」「ログ管理」を消すのではなく適切な下位に収める。
superadminの顧客切替は常時表示し、現在の顧客名とテスト/本番の表示を固定する。
顧客閲覧画面と受講者画面はこの管理ナビを流用しない。既存viewerは最小権限の顧客ロールと同一ではない。

### 4.2 デザイン方針

対象は業務管理画面。画面の一番大切な役割は「次に必要な作業を誤りなく終える」こと。
KPIカードを並べる案と、作業待ちを中心とする案を比較し、後者を採用する。

- 色: Ink `#19324A`、Action `#146C78`、Canvas `#F5F7FA`、Text `#243746`、Warning `#9B6100`、Danger `#B42318`。成功/危険は文字とアイコンも併用する。
- 文字: 見出しは游ゴシック太字、本文はメイリオ/システムsans、件数・時刻は等幅数字。導入時にOS差と折返しを検証し、外部Webフォントは必須にしない。
- レイアウト: 左ナビ＋主作業面＋必要な時だけ開く右HELP。カードの装飾を抑え、一覧には保存条件・列選択・ページングを共通装備する。
- 固有の視覚要素: キャンペーンを開くと「準備→検証→配信→観測→フォロー→報告」の進行帯が常に見える。APIの状態と区別し、完了条件と未完の理由を表示する。
- 主要操作には文字ラベルを付ける。色だけの判定、アイコンだけの送信、モーダルの多重化を避ける。
- 設計目標: キーボード操作、見えるfocus、読み上げ用ラベル、200%拡大、360px受講画面、動きを減らす設定への追従。適合を宣言するには実測が必要。

### 4.3 運用ホームのワイヤーフレーム

以下の件数は架空の表示例であり、実データではない。

---------------------------------------------------------
今日の要対応
  配信前の確認待ち       2件  → 内容と対象者を確認
  報告の照合待ち         3件  → 報告受付

---------------------------------------------------------

### 4.6 HELPを製品機能として実装する

右側の文脈HELPは「いま何を設定するか」「結果はどう変わるか」「困ったら何を調べるか」を説明する。
初期セットは次の8本。コードと同じリリースで更新し、記事ごとに対象ロール、画面ID、最終確認版を持つ。

1. 初めての訓練: 対象者登録→環境確認→テスト→配信→結果。
2. 少量プレビューと全件転送テストの違い、実際に送る通数。
3. メールが届かない: 送信未実行/SMTP受付/受信側隔離を分けて確認。
4. 開封・サイト表示・入力・報告・教育完了の意味と集計対象。
5. 操作していないのに計上された: スキャン判定の確認と訂正申請。
6. 報告の方法: 顧客のメール環境別、添付転送の手順、標準ボタンとの違い。
7. 教育の期限と催促: 対象、通知回数、途中再開、リンク期限切れ。
8. 顧客向け月次報告の作成: 確定値/暫定値、比較できない条件、注意書き。

検索・用語辞書・関連手順・問い合わせ用の匿名診断IDを提供する。ログや入力値をそのまま問い合わせへ添付しない。
操作不能の理由はボタン付近に出す。最初から生成AIチャットを導入せず、版管理した一次HELPを先に整える。

## 5. 仕様の中核

### 5.1 説明できる集計

- 指標ごとに分子・分母・集計単位・観測期間・除外条件・確定版を保存/表示する。
- 人数ベースの主指標: 「期間中に訓練メールがSMTPに受理された対象者のうち、確認済み報告をした人数」。SMTP受理を実配送・閲読の保証と表現しない。従来の対象数ベース指標は別名で併記する。
- 全コンテンツ配信では、人物×キャンペーンの割合とtracking_id単位の反応を分ける。同一人への複数通を人数に重複計上しない。
- 初動時間は該当する送信受付時刻から報告メール受信時刻まで。取込ジョブ実行時刻で代用しない。欠損・負値は除外理由と件数を示す。
- 報告率に、未照合・保留を勝手に加算しない。「クリック前に報告」と「クリック後に報告」は両方の行動を残す。
- bot判定、担当者の訂正、レポート確定は履歴を残す。過去納品済みレポートを無言で書き換えない。
- リスクスコアは事故確率ではなく支援優先度。現行の50点起点・重みは実証済みモデルではない。未観測を別表示し、方式を変える時はscore_versionを付ける。
- 少人数集計・部署異動・難易度差は比較の注意を表示。顧客向けには小集団の個人推測を抑える閾値を合意する。

9/5のKPI文書の報告率0%は取込実装前であり、現在の報告行動や新機能効果の比較基準にしない。

指標の原記録はS01aで次の対応を確定する。現行workerはバッチ終了後の同期で `campaign_targets.sent_at` を現在時刻に設定し、`delivery_log` を追加するため、その時刻を各メールのSMTP受理時刻として扱わない（`bin/tet2-worker.py` の `_sync_send_status()` / 配信ログ処理）。

| 指標 | 原記録・結合キー | 不足時の扱い |
|---|---|---|
| SMTP受理人数 | 送信側のrecipient別受理結果→tracking_id→campaign/target/tenant | 未同期・成否不明を別表示。送信済み行を再送して検証しない |
| 初動時間 | recipient別SMTP受理時刻＋報告側の受信時刻、tracking_idで照合 | S06で送信側の記録を補強。過去分は算出不能とし、batch終了時刻やメールDateから推定しない |
| 報告率 | 確認済みreportと対象snapshot、人物×campaignに集約 | 保留・未照合を別表示。確定後の訂正は新版 |
| 教育完了率 | 割当snapshot＋完了記録＋教材版 | 対象・版・期限が不明なら比較不可 |

### 5.2 半自動化の安全境界

対象条件 → 人数・理由preview → 対象snapshot → draft作成 → 人の確認 → 既存launch、の順にする。
条件セットは部署・group・行動・教育状況から始め、任意SQLや複雑な汎用workflow editorは作らない。
条件変更、データ更新、退職・停止、tenant切替は必ず再評価。送信直前も停止者等の除外を確認し、確定人数の変化を記録する。
再通知・教育割当にはidempotency key、cooldown、1人あたりの上限、静穏時間、履歴、手動停止を持たせる。
SMTP処理の成否不明は自動再送しない。安全な再送は別にrecipient単位のattempt管理を設計する。

### 5.3 権限とデータ保護

- UIの表示制御だけでなく、API・検索・CSV/PDF・background jobすべてでtenant/roleを再検証する。
- tenant切替で一覧cache、選択対象、未保存draft、HELP内の顧客固有情報を切り替える。古い非同期応答を描画しない。
- 偽認証画面の入力本文は、顧客承認参照・HTTPS・新規生成ページが揃う時のみ専用APIへPOSTし、DB外の鍵でAEAD暗号化する。通常イベント・ログ・CSV/XLSXへ本文を流さず、復号はシステム管理者のみ。キャンペーン削除時、または配信終了・統計確定後のクローズ時に暗号文を同一transactionで消去する。クローズ後は再収集・確定解除・再確定を拒否する。既存ページの置換/公開停止/共用受信側対処は別の本番変更承認後に実施し、過去ログの保持/削除とも切り分ける。
- .emlは危険な内容として隔離表示。リンクは自動訪問しない。外部評判照会はURL/ハッシュでも情報開示になり得るため、顧客同意と表示を設ける。
- rawメールの保持期限、アクセス権、バックアップ上の保持、削除監査を仕様化する。分類が「安全」でも自動開放しない。
- 顧客外部ポータルより前にSSO/MFA・閲覧専用権限・監査・セッション管理を完了させる。管理者MFAは利用人数の少なさだけを理由に先送りしない。
- 四眼承認は一人運用に強制しない。二人運用/顧客自身の配信開始時に、自己承認禁止と編集後の承認失効を追加する。

## 8. 技術構成・移行の原則

共通shell → 画面別JS → 既存 `api/*.php?action=...` → 業務service → SQLite、という構造を段階的に整理する。
`app.js`の3,714行を一括で書き換えず、既存の独立assetパターンに合わせて画面単位に切り出す。
URLへPIIやtokenを載せない。表示状態と未保存draftの保存先を区別し、機微情報をlocalStorageへ恒久保存しない。

| 選択肢 | 判断 |
|---|---|
| 既存Bootstrap＋画面別JSへの整理 | 推奨。配備とテストを維持し、UX改善を早く検証できる |
| 新画面だけTypeScript化 | 型の問題が実測で増える場合に検討。build/CSP/deployを先に確認 |
| React/Next.js・DBの全面置換 | 今回は採用しない。ユーザー価値より先にmigration費用が発生する |

データ追加の候補は `audience_rules`、対象snapshot/確認revision、scenario版、通知台帳、判定訂正履歴、指標version。名前・DDLは各Stepの設計時に確定する。
既存の `suspicious_mail_history`、`campaign_report_snapshots`、教育関連表で足りる責務を新表へ重複させない。
重い集計・PDFは必要時にジョブ化し、SQLiteの長時間write lockを避ける。負荷目標はS02で測定環境を固定して決める。
新依存はライセンス・保守状況・権限を監査してから採用。今回の調査ではOSSやMCPをインストールしていない。

GitHub remoteはあるが、既定branch参照は未設定、activeなgh認証にはエラーがあった。計画作成には支障なし。
実装時にremote/認証を確認して独立branch・小さいPRに分ける。確認できなければlocalの差分レビューで進め、remote設定/アカウントを無断変更しない。

Stepの分割/順序変更/撤回は理由、影響する依存、戻し方を記録。既に実装された機能を再度「新設」にしない。
共用受信endpoint、メールサーバー、実在宛先への送信、timer有効化、顧客公開、過去データ削除は個別の権限と変更計画が必要。
