# 07. 実機調査にもとづく TET v2 アップデート設計書（セキュリオ比較）

対象システム: TET v2（標的型メール訓練およびセキュリティ教育システム）
版: 2026-09-25 作成、2026-09-26 に受講者側の確認と全件撮影の結果を追記。
TET v2 はリポジトリ HEAD `9aafa33` の実装、セキュリオは 2026-09-24〜26 に閲覧した画面に基づく。
位置づけ: 本書は、競合製品セキュリオの管理画面を実際に閲覧して得た仕様とデザインの所見を、TET v2 の改修設計へ落とし込む。
全体の方向と優先順位は [GUI と機能の刷新計画](../../plans/tet2-product-renewal-20260923.md)（以下「刷新計画」）を正とし、本書はその各 Step を実機の事実で補い、刷新計画にない機能を追加候補として示す。

## 1. 目的と調査の範囲

刷新計画は、競合の公式ヘルプを根拠に作られており、競合の画面を実際に操作した検証を含んでいない。
本書の目的は、その不足を実機の閲覧で埋め、TET v2 で何をどの順に作るかを、データ、API、画面の粒度で決めることにある。

調査は、組織管理者の権限を持つトライアル環境で行った。
当初の巡回では閲覧だけを行い、訓練の作成や配信、eラーニングの受講、テストやアンケートの回答、設定の保存は一切していない。
これを仕組みで担保するため、ブラウザの通信のうち、ログイン認証と、一覧の読み取りに使われる問い合わせ以外の書き込み系の通信（POST、PUT、DELETE）をすべて遮断した状態で画面を巡回した。

2026-09-25 には、利用者の許可を得て、テスト用の受講者アカウント1つに限って書き込みを行い、受講者側の流れを確かめた。
調査用のカリキュラム、アンケート、訓練を作成してそのアカウントだけに配信し、受講、テストの解答、アンケートの回答、訓練メールの受信とクリックまでを行った。
書き込みは、送られる手続きを遮断した状態で先に確かめ、その手続きだけを許可して実行した。
削除の操作はしていない。

取得した画面は、当初の巡回が同じ URL の重複を除いて369画面である。
2026-09-25〜26 には、一覧の全ページと同じ形の詳細の全件を撮り直し、一覧の件数と撮影数を突き合わせた（2,867画面）。
キャプチャ、画面台帳、文言抜粋、所見メモは、実在の利用者名が写っているため、リポジトリの外（`/root/tet2-research/seculio-2026-09-24/`）に置いた。
本書には利用者名、メールアドレス、IP アドレス、調査に使ったテナントの組織名を載せない。

セキュリオの画面の文言、訓練文面、設問は複製しない。
本書では、確認した仕様を「パターン」と「要件」に言い換えて記述する。

## 2. セキュリオの構成と設計上の特徴

### 2.1 機能の構成

セキュリオは、機能ごとに独立した管理画面を持ち、ホームから各機能へ入る構成を採る。
旧来の画面（組織設定、社内アンケート）と、新しい単一ページアプリケーションの画面（メール訓練、eラーニング、セキュリティアウェアネス、フィッシング報告、自動連携）が併存している。

| 機能 | 確認した主な画面 | TET v2 で対応する領域 |
|---|---|---|
| メール訓練 | 訓練一覧（通常、定期、テスト）、訓練詳細（6タブ）、訓練テンプレート、ドメイン、種明かしページ、履歴、会社設定 | キャンペーン、定期キャンペーン、テンプレート、到達画面、レポート |
| セキュリティアウェアネス | リテラシースコア、配信状況、問題一覧、タグ、スコア管理、解答状況 | 教育の確認テスト、教育レポート |
| eラーニング | カリキュラム、レッスン、受講履歴、カリキュラム詳細（6タブ） | 教材、教育配信、受講 |
| フィッシング報告 | 報告メール（訓練と訓練以外）、ダッシュボード、オートメーション（タグ、ルール、アクション）、返信テンプレート、通知文面 | 報告メール、不審メール |
| 自動連携 | シナリオ一覧、シナリオ詳細（条件、実行内容、実行履歴） | 教育の自動割当 |
| 社内アンケート | アンケート一覧、作成、配信、全体回答、利用者別回答 | なし |
| 組織設定 | 利用者、権限、グループ、パスワード方針、SAML、SCIM、IP 制限、通知 | 管理アカウント、対象者、グループ |

### 2.2 画面設計のパターン

一覧画面は、どの機能でも同じ部品で組み立てられている。
件数の表示（全体件数と表示範囲）、表示件数の切替、列見出しでの並べ替え、折りたたみ式の詳細検索、チェックボックスと「まとめて操作」、検索結果の CSV 出力の6点が共通で、主操作のボタンは右上に1つだけ置かれる。

詳細画面は、固定のタブで情報を分け、タブごとに URL を持つ。
訓練詳細のタブは、結果、メール内容、配信設定、利用者ごとの状況、グループごとの集計、行動履歴の6つであり、タブの URL を共有すれば同じ画面を開ける。
設定が終わっていないタブには「未設定」のバッジが付き、画面上部の帯に「内容の設定、配信の設定、配信」の3段階の手順と現在位置が表示される。

結果の見せ方は、訓練の形式によって変わる。
リンク型ならクリック、返信、報告の3指標、添付型なら添付の開封、返信、報告の3指標だけを円グラフで示し、それぞれに人数、母数、割合を併記する。
形式と関係のない指標を並べないことで、0% が「起きなかった」のか「測っていない」のかを読み手が取り違えにくくしている。

空の状態と注意書きにも型がある。
データがない画面は、理由を一文で述べる表示にそろえている。
計測の限界（利用者が何もしていなくても、受信側のセキュリティ製品によって既読やクリックが記録されうること）は、訓練のすべての画面の上部に常に表示されている。

### 2.3 仕様上の特徴

設計に影響する仕様上の特徴は次の8点である。

- **行動判定の記録と訂正**：行動履歴は1行動1行で、行動、配信から行動までの時間、IP、OS、ブラウザに加えて、「セキュリティ製品による行動か、利用者による行動か」の判定と、自動返信の判定を持つ。
  判定は管理者が後から直せ、最終更新者と日時が残る。
  会社設定には、自動返信を防衛失敗として扱うかの方針と、利用者による行動とみなす IP の許可リストがある。
- **宛先の品質管理**：利用者ごとにメールアドレスの状態（利用可能、利用不可、受信側から拒否、検証中）を持ち、使えない宛先の件数を一覧の上部で警告する。
  訓練の配信対象の人数表示でも、無効な利用者、宛先が使えない利用者、削除済みの利用者の内訳を示す。
- **機能間の連携**：訓練メールの設定画面から「防衛に失敗した利用者へ eラーニングを配信する」を直接指定できる。
  より一般的には、自動連携のシナリオで「条件に合う利用者を抽出し、N 時間後に別機能の処理を実行する」を定義でき、1人に対して1回だけ実行され、実行履歴が残る。
- **小問の高頻度配信とタグ別スコア**：セキュリティアウェアネスは、1回数問の小テストを毎週や四半期ごとに配り、設問に付けたタグ（10のメインタグと約30のサブタグ）ごとに理解度を集計する。
  総合スコア、正答率、受講完了率を並べ、全社、グループ、利用者の単位で推移を見られる。
  解答は1問1行で、所要時間まで記録される。
- **報告の自動応答**：報告されたメールに対し、タグ、ルール、アクションの組合せで確認と返信を自動化できる。
  返信の文面はテンプレートとして管理し、訓練メールを正しく報告した人への御礼、確認開始の連絡、安全か危険かの結果共有などを使い分ける。
- **訓練と連動するアンケート**：訓練後の振り返り用の設問（不審に気づいたか、報告しなかった理由、今後の行動など）を、予約配信と締切前の催促付きで配る。
  配信した後は設問を編集できない。
- **訓練メールの識別**：訓練メールは訓練専用のドメインから送られ、送信ドメイン認証（SPF、DKIM、DMARC）をすべて通っていた。
  受信者は、独自のメールヘッダーと、リンクのパスに入れた識別子の2か所で区別される。
  この識別子は、報告されたメールが訓練メールかどうかを見分ける手掛かりにもなる。
- **行動の記録の単位**：同じ利用者が同じリンクを2回開くと、行動履歴には2行が残り、結果の集計は人数として1人と数える。
  受講者側の確認では、利用者の実際のクリックが「利用者による行動」と判定された。

TET v2 の現状は、リポジトリのコードで確認した事実を根拠にする。
「差の評価」は、TET v2 の運用と顧客への約束に照らした判断である。

| ID | 領域 | セキュリオで確認した仕様 | TET v2 の現状（根拠） | 差の評価 | 刷新計画 |
|---|---|---|---|---|---|
| G01 | 行動判定の記録と訂正 | 装置による行動も記録して判定を付け、手動で訂正でき、IP の許可リストを持つ | ボットの User-Agent によるクリックと報告は、記録せずに捨てる（`EventIngest::isBotUserAgent`）。除外の判断基準はコードのコメントに残るが、実行時に除外した件数と個別の行はデータベースに残らない | 大。除外の実績を顧客へ示せず、誤判定を直せない | S06 |
| G02 | 自動返信の扱い | 自動返信を防衛失敗とみなすかを会社ごとに設定する | 報告メールの解析は `Auto-Submitted` を検出する（`ReportMailParser`）。返信行動の記録で自動返信を区別しているかは未確認 | 中。方針を持たないと返信率が不安定になる | S06 |

次の機能は、確認したうえで TET v2 に取り入れない。
理由は第8章に記す。

- SAML と SCIM による利用者連携、IP アドレス制限

- 訓練メールと受講画面の自動翻訳

## 4. 設計方針

本書の設計は、刷新計画の安全境界を引き継ぐ。
対象の抽出、人数と理由の確認、対象の固定、下書きの作成、人の確認、既存の起動操作、の順を崩さない。
教育やアンケートのメールを実在の従業員へ送る処理は、実装してもタイマーを有効にせず、有効化は利用者の明示の承認を得てから行う。

データは、既存のテーブルで表せる責務を新しいテーブルへ重複させない。
新しいテーブルと列は、`web/db/MigrationRunner.php` の版として追加し、`web/tests/fixtures/TestDatabase.php` にも同じ定義を足す。
版の名前は本書の案であり、各 Step の設計時に確定する。

画面は、既存の Bootstrap と画面別の JavaScript の構成に合わせる。
セキュリオの配色やアイコン、文言は使わず、刷新計画 4.2 のデザイン方針（Ink、Action、Canvas の配色、文字ラベル付きの主要操作）に従う。

## 5. 機能別の設計

各機能には U 番号を振り、第3章の差（G 番号）と刷新計画の Step に対応づける。

### 5.1 U1 行動判定の記録と訂正（G01、G02、S06）

**目的**：装置による行動を捨てずに記録し、集計から除外した理由を示し、誤判定を担当者が直せるようにする。

**データ**：`events` は利用者による行動だけを持つテーブルとして残し、集計から外した行動を新しいテーブル `excluded_events` に記録する。
`events` に判定の列を足して同じテーブルに入れる案は採らない。
`events` には `UNIQUE (tracking_id, event_type, occurred_at)` の一意制約があり、装置による行動を先に記録すると、同じ秒に起きた利用者の行動が一意制約で捨てられるおそれがある。
加えて、集計する側（`report.php`、`HumanRiskScore`、`EduAutoEnroll`、`followup.php`）のすべてに除外の条件を足す必要があり、1か所の漏れで装置の行動が集計に混ざる。
別のテーブルに分ければ、既存の集計は変更なしで正しいままになる。

`excluded_events` は、`events` と同じ列（テナント、キャンペーン、tracking_id、行動の種類、発生日時、取得元、原文）に、次の列を加えて持つ。

- `actor_class`：`scanner`（セキュリティ製品や自動取得）、`auto_reply`（自動返信）、`unknown` の3値。
- `class_reason`：判定の根拠（一致した User-Agent の語、`Auto-Submitted` の値など）。
- `class_source`：`auto`（取込時の自動判定）か `manual`（担当者の訂正）。

`excluded_events` にも `events` と同じ `UNIQUE (tracking_id, event_type, occurred_at)` を置き、同じ秒の重複したアクセスは `INSERT OR IGNORE` で1行にまとめる。
装置は同じリンクを短時間に何度も取得することがあるため、件数は行数ではなく「除外した行動の有無」として扱う。
判定の訂正は、行を `events` と `excluded_events` の間で移す操作とし、その履歴を新しいテーブル `event_class_history`（テナント、tracking_id、行動の種類、発生日時、変更前と変更後の区分、理由、変更者、変更日時）に残す。
テナントごとの方針は新しいテーブル `tenant_training_settings` に置き、自動返信を失敗として数えるか（`auto_reply_policy`）と、利用者の行動とみなす IP の許可リスト（`human_ip_allowlist`）を持たせる。

**取込の変更**：`EventIngest` の、ボットの User-Agent に一致した行を読み飛ばす処理を、`excluded_events` へ `scanner` として記録する処理に置き換える。
現行の除外はクリックと報告だけに適用され、偽サイトのビーコン（`open`）は意図して除外していない（メールクライアントの先読みで踏まれる性質のため、開封として数える判断がコードに記されている）。
本設計はこの適用範囲を変えず、`open` は従来どおり `events` に記録する。
許可リストに一致する IP の行動は、User-Agent に関係なく `events` に記録する。
既存の `events` の行は、これまでボットの行を保存していないので、意味が変わらない。

**API**：`logs.php` に、除外した行動の一覧と、判定を訂正する操作（`event_reclassify`、POST、operator 以上、CSRF トークン必須）を追加する。
訂正は、行の移動と履歴の記録を1つのトランザクションで行う。
移動先に同じ組の行がすでにある場合は、移動先の行を残して移動元の行を削除し、その旨を履歴に記録する。
確定済みの集計（`campaign_report_snapshots`）は書き換えず、再確定が必要であることを画面に示す。

**画面**：U2 のキャンペーン詳細の「行動履歴」タブに、利用者の行動と除外した行動を切り替えて表示し、判定区分、根拠、訂正の操作を置く。
計測の限界の注記を、キャンペーン詳細の上部に常に表示する。

**検証**：`web/tests/event_ingest_bot_filter_test.php` を、ボットの行が `excluded_events` に記録され、`events` に入らないことを確かめる内容に改める。
訂正の前後で集計値が変わること、確定済みの集計が変わらないこと、他のテナントの行動を訂正できないこと、移動の途中で失敗しても行が失われないこと、移動先に同じ組の行がある場合の扱い、`open` が従来どおり `events` に入ることを新しいテストで確かめる。
既存の `php web/tests/api_report_test.php` と `php web/tests/human_risk_score_test.php` が変更なしで通ることも確かめる。

### 5.2 U2 キャンペーン詳細の固定タブ（G03、G05、G06、S04、S06）

**目的**：1件のキャンペーンの設定、配信、結果、行動を、1つの画面の6つのタブで確かめられるようにする。

**画面**：キャンペーン詳細を次の6タブで構成し、タブごとに画面の URL（刷新計画 S03 で導入した画面 URL の復元を使う）を持たせる。

1. 結果：訓練の形式（リンク、添付、QR、認証入力）に応じた指標だけを、人数、母数、割合の組で示す。
   母数と除外の条件は刷新計画 5.1 の指標の定義に従う。
2. 内容：件名、本文、到達画面、種明かしページのプレビューと、行動から計測までの流れの図。
3. 配信設定：送信期間、分割数と間隔、営業時間の条件と、全員へ送り終えるまでの見込み時間。
4. 対象者ごとの状況：配信の結果と、行動の種類ごとの初回日時。
5. 部署ごとの集計：会社と部署の属性で集計する（G14 のとおり、階層グループは作らない）。
6. 行動履歴：U1 の判定区分付きの一覧。

設定が終わっていない項目があるタブには「未設定」の印を付け、配信前確認の画面の6段階の表示（準備、検証、配信、観測、フォロー、報告）と同じ位置づけで現在の段階を示す。

**見込み時間の計算**：送信スケジュールが作成済みなら、`send_schedule` の最初と最後の予定時刻から求める。
作成前は、分割数、分割間隔、営業時間帯、営業日の設定から計算し、「予定」と明示する。
実際の送信時刻とは異なりうるため、見込みを約束の値として表示しない。

**API**：`report.php` に、1件のキャンペーンの結果タブ用の集計（`campaign_overview`）を追加する。
他のタブは、既存の `campaigns.php`、`campaign_launch.php`、`report.php` の個人別集計、`logs.php` の行動一覧を、キャンペーン指定で呼び出す。
データベースの変更は要らない。

**検証**：`php web/tests/campaign_editor_ui_test.php` と `php web/tests/api_report_test.php` に、結果タブの指標が形式ごとに切り替わること、母数が集計と Excel で一致することを追加する。
画面は 1280px と 1440px、キーボード操作で確認する。

### 5.3 U3 宛先の到達性の管理（G04、S08）

**目的**：届かない宛先を把握し、配信の分母と配信前確認に反映する。

**データ**：`targets` に次の列を追加する。

- `email_status`：`unknown`、`ok`、`rejected`（送信時に拒否された）、`bounced`（不達の通知を受けた）の4値。
- `email_status_at`、`email_status_reason`：状態を更新した日時と根拠。

状態の更新元は、第1段階では `delivery_log` の SMTP 結果だけとする。
不達の通知メール（DSN）の解析は、報告メールの取込と同じ受信箱の扱いを決めてから第2段階で行う。
セキュリオの画面には宛先の一括検証があるが、TET v2 では検証のためのメールを送らない。
実在の従業員へ送信が発生するためである。

**画面と配信前確認**：対象者の一覧に状態の列と、使えない宛先の件数の警告を置く。
配信前確認では、`rejected` と `bounced` の宛先を警告として示し、対象から外すかどうかは担当者が選ぶ。
自動で除外すると、宛先の一時的な障害で訓練の対象から漏れる人が出るためである。

**検証**：合成の `delivery_log` から状態が更新されること、他のテナントの状態を変えないこと、配信前確認の警告件数が一致することをテストで確かめる。

### 5.4 U4 訓練後のフォロー規則（G06、G07、S08、S09）

**目的**：「どの行動をした人に、いつ、何をするか」を規則として定義し、実行の前に対象を確かめられるようにする。

**既存の仕組みとの関係**：`EduAutoEnroll` は、教育配信の `triggered_by = 'phishing_failure'` と `phish_campaign_id` を使い、認証入力かクリックをした人を教育へ割り当てる。
本設計はこの仕組みを置き換えず、条件と実行内容の種類を増やし、実行前の確認と実行履歴を加える。

**データ**：新しいテーブル `followup_rules` と `followup_rule_runs` を追加する。
`followup_rules` は、テナント、名称、状態（下書き、有効、停止）、対象キャンペーン（未指定なら全キャンペーン）、条件とする行動の集合（クリック、認証入力、添付の開封、返信、報告）、抽出から実行までの遅延、実行内容の種類と参照先を持つ。
実行内容の種類は、教育配信への割当、アンケート配信への割当（U7）、種明かしメールの下書き作成の3つから始める。
`followup_rule_runs` は、規則、対象者、キャンペーン、実行日時、結果を持ち、規則と対象者の組に一意制約を置いて、1人1回の実行を保証する。

**実行の安全境界**：規則を有効にしても、メールは送らない。
種明かしメールは、TET v2 にまだない新しい送信経路であり、送信の処理を実装しても既定で停止とする（テナント単位の有効化フラグを既定で無効にし、送信用のタイマーは作っても有効にしない）。
有効化は、`tet2-edu-enroll` と `tet2-edu-reminder` と同じく、利用者の明示の承認を得てから行う。
規則の実行が作るのは、教育やアンケートの割当と、種明かしメールの下書きまでであり、送信は既存の送信の承認と、停止中のタイマーの方針に従う。
規則の画面には、今の条件で抽出される人数、理由、前回からの増減を示し、刷新計画 5.2 の条件のプレビューと対象の固定の手順を通す。
条件の判定には `events` の行動だけを使い、U1 で除外した装置の行動（`excluded_events`）は使わない。
停止中のタイマーの有効化を検討できる基準は、合成環境で規則の再実行と多重起動による重複が0件であること、1顧客での試行で割当と通知の対象が担当者の確認と一致したこと、送信の緊急停止の手順を確認したことの3点とし、刷新計画 S12 の評価の場で判断する。

**検証**：`php web/tests/edu_auto_enroll_test.php` に、同じ規則を繰り返し実行しても割当が重複しないこと、装置による行動で割当が起きないこと、他のテナントの行動を拾わないことを追加する。

### 5.5 U5 分野別の理解度評価（G09、追加）

**目的**：確認テストの結果を分野別に集計し、組織の弱い分野と推移を示す。
ゴールドウイン様向け提案書の「⑤ 理解度テスト」を、分野別に説明できる形にする。

**分類の設計**：教材カテゴリ（`edu_categories`）は教材の棚分けとして残し、設問の分類には新しい2階層のタグを使う。
1つの設問が複数の分野にまたがるのは珍しくないため（パスワードの設問が端末管理にも関わる、など）、設問とタグを多対多で結ぶ。
タグの体系は TET v2 独自に定める。
初期案は、認証、端末、メールとコミュニケーション、情報資産、委託先、サイバー攻撃、社外と在宅、インシデント対応、生成 AI、法令と規程の10分野とし、各分野に2〜5のサブタグを置く。

**データ**：新しいテーブル `edu_tags`（テナント、親タグ、名称、説明、並び順、共有区分）と `edu_question_tags`（設問、タグ）を追加する。
`edu_response_answers` に解答の所要時間（`answer_ms`）を追加する。
分野別のスコアは、既存の `edu_score_snapshots.category_scores` と同じ形の JSON を新しい列 `tag_scores` に保存し、計算方式の版（`score_version`）を付ける。

**スコアの定義**：分野別の正答率を「その分野のタグが付いた設問への解答のうち、正解した割合」と定める。
受講完了率は「配信した小テストのうち、期限内に完了した割合」とし、正答率と混ぜた単一の総合点は作らない。
セキュリオの総合スコアは正答率と異なる値を示しており、計算方法が画面から読み取れなかったため、同じ数値を再現しようとしない。

**定期の小テスト**：教育配信の種別 `awareness_quiz` に、繰り返しの規則（週ごと、月ごと、四半期ごと）と1回あたりの設問数を持たせ、配信の下書きを定期的に作る。
下書きの生成は定期キャンペーンの仕組み（`CampaignAutomationSchedule` の規則の書き方）にそろえ、配信メールの送信は教育のタイマーの承認方針に従う。

**画面**：教育の画面に「理解度」を加え、正答率、受講完了率、分野別の値、推移、部署ごとの行列を示す。
既存の教育レポートが表示する教材カテゴリ別の値（`category_scores`）は、教材の棚分けごとの成績として名称を「教材カテゴリ別」に改めて残し、分野別の理解度は新しい「理解度」の画面だけに表示する。
同じ画面に2つの体系の値を並べないことで、同じ受講者について異なる印象を与えることを避ける。
少人数の部署は、個人が推測できないよう、人数が閾値に満たない場合は値を表示しない。

**検証**：タグ付けした合成設問と合成解答で、分野別の正答率、完了率、少人数の非表示を確かめる。
既存の `php web/tests/api_edu_report_test.php` の値が変わらないことも確かめる。

### 5.6 U6 報告者への返信（G10、G11、S07）

**目的**：報告した従業員へ、確認を始めたこと、訓練メールだったこと、安全か危険かの結果を返し、報告を続ける動機をつくる。

**データ**：新しいテーブル `report_reply_templates`（テナント、名称、用途、本文、差し込み変数）と `report_replies`（報告メール、テンプレート、送信時点の本文、状態、作成者、送信者、送信日時）を追加する。

**動作**：報告メールが訓練のキャンペーンと照合できた場合、「訓練メールだった」用途のテンプレートで返信の下書きを作る。
刷新計画 S07 のとおり、返信は自動送信せず、担当者が内容を確かめて送る。
送信は既存の SMTP 経路（`localhost:25`）を使い、返信の本文に報告者以外の個人情報を差し込まない。

セキュリオのタグ、ルール、アクションによる自動化は、第1段階では採用しない。
報告の件数が少ないうちは、下書きと手動の送信で足り、規則の誤作動による誤った「安全」通知のほうが害が大きいためである。

**画面**：報告受付の画面に、返信の下書き、送信済みの返信、テンプレートの管理を置く。
月次の報告数と報告者数を、訓練メールと実メールで分けて示す。

**検証**：`php web/tests/report_mail_ingest_test.php` に、照合できた報告だけに下書きが作られること、同じ報告に二重の下書きが作られないこと、他のテナントのテンプレートを使えないことを追加する。

### 5.7 U7 アンケート（G12、追加）

**目的**：訓練や教育の後に短いアンケートを配り、気づきや報告しなかった理由を集める。
ゴールドウイン様向け提案書の「⑥ アンケート」（年2回）を実現する。

**データ**：新しいテーブルを5つ追加する。

- `surveys`：テナント、題名、説明、状態（下書き、配信済み、終了）、匿名の有無、作成者。
- `survey_questions`：アンケート、節、並び順、形式（単一選択、複数選択、自由記述）、必須、選択肢、表示条件（前の設問の回答による分岐）。
- `survey_deliveries`：アンケート、配信日時、締切日時、状態、対象の固定（対象者の一覧）。
- `survey_assignments`：配信、対象者、受講用トークン、状態、回答日時。
- `survey_answers`：回答の単位、設問、値。

匿名のアンケートでは、`survey_answers` を `survey_assignments` と結ばず、配信ごとの無作為な識別子だけで回答をまとめる。
回答したかどうかは `survey_assignments` で管理し、どの回答が誰のものかはデータベースからもたどれないようにする。

**編集の制限**：配信を始めたアンケートは、設問を編集できない。
配信後に設問が変わると、同じ集計に異なる設問への回答が混ざるためである。
変更が必要な場合は、複製して新しいアンケートとして配る。

**受講者の画面**：教育の受講と同じトークン方式を使い、`take.php` の構成に合わせた回答画面を用意する。
管理画面には入れない。

**配信**：第1段階では、配信を作ると受講用の URL の一覧を CSV で出力し、担当者が顧客の社内メールで配布する。
第2段階で、教育と同じ送信の仕組みでの案内と、締切前の催促を追加する。
どちらの段階でも、送信の有効化には利用者の承認を要する。

**集計と出力**：全体の回答率、設問ごとの回答分布、部署ごとの回答率を示し、Excel（`SimpleXlsx`）と CSV で出力する。
匿名のアンケートでは、利用者別の回答を表示しない。

**雛形**：訓練後の振り返り（不審に気づいた点、報告したか、報告しなかった理由、今後の行動）と、教育後の理解の確認の2種類を、TET v2 の文面で用意する。

**検証**：配信後の編集の拒否、匿名時に回答と対象者が結び付かないこと、トークンの不正と期限切れ、他のテナントのアンケートへの回答の拒否を、合成データのテストで確かめる。

**実装状況（2026-09-25）**：利用者の承認を得て、第1段階と第2段階をリポジトリ内に実装した（本番未配備、commit 未実施）。
メール送信は環境変数 `TET2_SURVEY_MAIL_ENABLED=1` のときだけ動き、既定は停止である。
催促は CLI（`web/db/survey_reminder.php`）までとし、systemd timer は作っていない。
回答の単位を `survey_responses` として独立させ、テスト用対象者の回答を集計から外す印（`is_test`）を持たせたため、テーブルは6つになった。
配備の条件は `deploy/README.md` に記した。

### 5.8 U8 シナリオの説明情報（G13、S05）

**目的**：シナリオを選ぶ根拠を、担当者と顧客が同じ情報で確かめられるようにする。

### 5.9 U9 一覧と詳細の共通部品（G15、S03）

**目的**：どの一覧でも同じ操作で探し、絞り込み、まとめて処理できるようにする。

## 8. 取り入れない機能とその理由

- **SAML、SCIM、IP 制限**：製品ロードマップの P3 と刷新計画の保留機能に同じ判断がある。
  管理者が少人数のうちは、外部 IdP の設定と退職者の無効化の設計を先に固める価値のほうが大きい。
- **Microsoft 365 と連携した検索とブロック**：顧客のメール環境の管理権限が必要であり、運用代行の範囲を超える。
  報告の受付と照合の精度を先に上げる。
- **YARA ルールや AI による報告の自動判定**：誤って「安全」と通知したときの害が大きい。
  刷新計画の「未検出を安全と断定しない」方針と両立しない。
- **自動翻訳**：現在の顧客はすべて日本語で運用している。
  多言語の需要が確認できた時点で再検討する。
- **キャラクターを使った演出**：業務管理画面の目的（次の作業を誤りなく終える）に寄与しない。
- **セキュリオの訓練文面と設問の流用**：権利上の問題があるうえ、TET v2 の強みである顧客別の日本語シナリオの調整と両立しない。
