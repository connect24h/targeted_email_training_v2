# 02. 基本設計書

対象システム: TET v2（標的型メール訓練およびセキュリティ教育システム）
版: 2026-09-24 時点の実装（リポジトリ HEAD `9aafa33`）に基づく。
位置づけ: 本書は全体構成と主要コンポーネントの責務、データ分離、送信の流れ、認証方式を定める。個々の API やテーブルの詳細は詳細設計書に置く。

## 1. 全体構成

TET v2 は、管理者が操作する Web アプリケーションと、メールを送信する常駐処理、定期処理を行うタイマー群、そしてこれらが共有するデータベースから成る。

構成要素は次のとおりである。

- **Web アプリケーション**（本番配置 `/var/www/html/tet2`）：管理画面（SPA）と REST API、リポジトリ層、データベースアクセス、生成物の置き場を含む。
- **メール送信処理**（本番配置 `/opt/training/bin`）：常駐する送信ワーカーと、SMTP 送信本体、生成用のスクリプトを含む。
- **データベース**（`/opt/training/tet2-db/tet2.sqlite`）：Web から到達できない場所に置く SQLite。WAL モードで運用する。
- **タイマー群**（systemd）：送信、権限補正、定期キャンペーンの下書き生成、報告メールの取込、教育の割当と催促、教育のスコア集計を実行する。

管理者はブラウザから SPA を操作し、SPA が API を呼ぶ。API はリポジトリ層を通してデータベースを読み書きする。訓練の配信は、API が送信スケジュールを作り、常駐ワーカーがそれを監視して送信する形で、Web と送信処理を分離する。

## 2. 主要コンポーネントと責務

### 2.1 管理画面（SPA）

`index.html` と `app.js`、`assets/` から成る単一ページアプリケーションである。
ログイン、運用ホーム、キャンペーン、レポート、ログ管理、リスク、教材、報告メール、不審メール、対象者やグループなどの管理を、作業の単位ごとの画面として提供する。
外部の配信網に依存せず、Bootstrap や Chart.js などのライブラリを `assets/vendor/` にローカル配置する。

### 2.2 REST API

`web/api/*.php` に置く。各ファイルは業務領域ごとに分かれ、`?action=` で操作を選ぶ。
参照は GET、変更は POST とし、変更には CSRF トークンを必須とする。外部連携の API は Bearer 認証を用いる。

### 2.3 リポジトリ層とサービス

`web/lib/` に、データベースアクセスと業務ロジックを置く。主なものは次のとおりである。

- **Db**：データベース接続と、テナント境界を保つ `forTenant()` を提供する。
- **PipelineRunner**：送信用 CSV の生成と、生成物の検証を担う。
- **CampaignLaunchService、CampaignPreflight、CampaignLauncher**：配信前確認と起動、生成物の準備を担う。
- **CampaignDraftFactory、CampaignAutomationRunner、CampaignAutomationSchedule**：定期キャンペーンの下書き生成を担う。
- **EventIngest、TrainingLogRows、GeoIpCache**：反応の取込、ログ行の生成、地域推定のキャッシュを担う。
- **HumanRiskScore**：リスクの評価を担う。
- **CredentialVault**：承認制で収集した入力値の暗号化と復号を担う。
- **ReportMailIngest、ReportMailParser、ReplyMaildir**：報告メールと実受信メールの取込と解析を担う。
- **SuspiciousMailAnalyzer、SuspiciousMailStore、VirusTotalClient**：不審メールの解析とレピュテーション照会を担う。
- **OfficeDocumentReader、SimpleXlsx**：教材の PowerPoint 取込と、設問の Excel 入出力を担う。
- **IntegrationAuth、Secrets**：外部連携の認証と、秘密値の取り出しを担う。

### 2.4 メール送信処理

`bin/` に置く。

- **tet2-worker.py**：常駐する送信ワーカー。送信スケジュールを監視し、送信期限が来たバッチだけを取り出して送る。
- **send_email.py**：SMTP 送信の本体。ローカルの `localhost:25` へ送る。v1 と共用する。
- **create_beacon_files.py、qr_doc_gen.py、replace_url.py**：ビーコン、リンク、QR コード付き文書、添付ファイルの生成を担う。
- **tet2-purge-campaigns.py**：論理削除したキャンペーンの物理的な消去を担う。

## 3. データ分離の方式

すべての業務テーブルはテナント識別子（`tenant_id`）を持つ。
アプリケーションはリポジトリ層の `Db::forTenant()` を通してデータベースへアクセスし、テナントの境界を保つ。あるテナントの操作が別のテナントのデータへ到達しないよう、参照系でも権限外参照を多重に防ぐ。
全テナントを横断する集計は、superadmin の一部機能に限る。

## 4. 送信パイプライン

訓練の配信は、Web 側の準備と、送信処理側の実行に分かれる。

準備（管理画面の起動操作）では、次を同期して実行する。

1. `PipelineRunner` が、データベースの内容から送信用 CSV を生成する。
2. `create_beacon_files.py` が、ビーコン、リンク、添付を生成する。
3. 全行の必須生成物を検証し、成功したときにだけ送信スケジュールを作成する。

実行（常駐ワーカー）では、`tet2-worker.py` が、配信中のキャンペーンの送信期限が来たバッチを取り出し、生成済みデータを再検証してから送信する。
送信の各通は、SMTP へ渡す直前に、対象者の在籍状態、所属、元のメールアドレスをデータベースで再確認する。不一致があれば残りの送信を止める。必須の添付が欠けていたり読めなかったりする場合は、本文だけで送らず、キャンペーンを一時停止する。

配信の緊急停止は、データ保存先に停止フラグを置くことで行う。フラグを検出したバッチは取り消し、キャンペーンは一時停止になる。

## 5. 認証と権限

管理画面は PHP セッションで認証する。ログインの失敗回数を数え、一定回数を超えたアカウントを一時的にロックする。
変更操作には CSRF トークン（`X-CSRF-Token`）を必須とする。
外部連携の API は Bearer 認証を用い、重複した実行を防ぐため idempotency キーを記録する。
権限は、参照が viewer 以上、変更が operator 以上を基本とし、認証情報の閲覧など強い操作はさらに限定する。

## 6. 定期処理

定期処理は systemd タイマーで実行する。役割は次のとおりである。

- 送信ワーカーの常駐。
- Maildir の権限補正。
- 定期キャンペーンの下書き生成。
- 報告メールの取込。
- 教育のスコア集計。
- 教育の割当と催促（既定では停止）。

教育の割当と催促は、実在の従業員へメールを送るため、既定で停止している。有効化は運用手順書の手順に従う。

## 7. 配備とロールバックの方針

本番への配備は、追跡済みのファイルと許可リストに載せたファイルだけを対象とし、既定では変更内容の確認（dry-run）にとどめる。実際の適用、本番データベースのマイグレーション、サービスの再読み込みは、それぞれ別の工程として承認のうえで行う。
配備の前にはバックアップを取り、問題があればロールバック手順で戻す。管理画面のアセットを変えたときは、内容に応じて URL が変わる仕組みで、古いキャッシュの利用を防ぐ。

## 8. 旧版との関係

TET v2 は旧版 v1（`/tet`）と別に構築し、当面は両者を共存させる。送信本体（`send_email.py`）は v1 と共用する。本書は v2 の設計だけを対象とし、v1 の設計文書とは別に管理する。
