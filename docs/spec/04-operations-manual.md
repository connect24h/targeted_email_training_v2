# 04. 運用手順書

対象システム: TET v2（標的型メール訓練およびセキュリティ教育システム）
版: 2026-09-24 時点の実装（リポジトリ HEAD `9aafa33`）に基づく。
位置づけ: 本書は配備、ロールバック、日常運用、障害対応の手順を定める。詳しい安全境界は `deploy/README.md` を、画面操作は利用マニュアルを参照する。

本システムは実在の従業員へメールを送る本番システムである。配備、データベースの変更、タイマーの有効化、メールの送信は、いずれも承認を得た手順でのみ行う。

## 1. 本番の構成

- Web: `/var/www/html/tet2`（受講者ポータルは専用のサブドメインで公開する）。
- メール送信: `/opt/training/bin`。
- データベース: `/opt/training/tet2-db/tet2.sqlite`（Web から到達できない場所、WAL）。調査は読み取りだけで行い、変更を伴う確認は複製に対して行う。
- 常駐サービス: `tet2-worker.service`。
- タイマー: 権限補正、定期キャンペーン、報告メール取込、教育スコア集計、教育の割当と催促。

旧版 v1（`/tet`、`/opt/training/git-repo`）と共存している。v1 の資産には触れない。送信本体（`send_email.py`）は v1 と共用する。

## 2. 配備

配備は許可リストに載せたファイルだけを対象とし、既定では変更内容の確認（dry-run）にとどまる。適用、マイグレーション、サービス操作は、それぞれ別の工程として承認のうえで行う。

### 2.1 アセットを変えたときのキャッシュ対策（配備前に必須）

`app.js`、`assets/app.css`、`assets/campaign-automations.js`、`assets/positions.js` のいずれかを変えたら、配備の前に次を実行し、参照 URL へ内容のハッシュを埋め込む。

```
deploy/tet2-cache-bust.sh
```

これを忘れると、ブラウザが古い `app.js` を使い続けて初期化が壊れる。冪等なので何度実行してもよく、忘れると `web/tests/cache_bust_test.php` が落ちて気づける。

### 2.2 差分の確認と適用

最初に差分とチェックサムを確認する。

```
deploy/tet2-deploy.sh
```

適用するとバックアップ ID を出力する。マイグレーションとサービス操作は別の工程として残る。

```
sudo deploy/tet2-deploy.sh --apply
```

特定の修正だけを配備し、未配備の他機能を巻き込まない場合は、範囲を指定する。

```
sudo deploy/tet2-deploy.sh --scope=campaign-safety
sudo deploy/tet2-deploy.sh --apply --scope=campaign-safety
```

### 2.3 マイグレーション

スキーマの変更が要る機能は、コードより先にマイグレーションを適用する。配備はマイグレーションを自動実行しない。複製に対して確認してから、`--apply` と、本番の場合はさらに `--allow-production` を付けて適用する。適用前には必ずバックアップを取る。

```
php web/db/migrate.php --db=/絶対パス/コピー.sqlite
php web/db/migrate.php --db=/絶対パス/コピー.sqlite --apply
```

機能ごとの順序に注意する。

- 配信時のテンプレート固定を含む配備では、`20260923-template-snapshots` を先に適用し、`campaign_template_snapshots` を確認してから新しい起動処理を有効にする。
- 承認制の入力値収集を含む配備では、`20260923-credential-captures` と `20260923-campaign-close` をコードより先に適用する。あわせて暗号鍵の準備（第4章）を済ませる。

### 2.4 配備後の確認

```
find /var/www/html/tet2 -name '*.php' -type f -exec php -l {} \;
apache2ctl configtest
systemctl daemon-reload
systemctl is-active tet2-worker.service
curl -fsS https://<受講者ポータルのドメイン>/tet2/ >/dev/null
```

`daemon-reload` 以降は外部の状態を変えるか参照するため、本番配備の承認後に実行する。
静的な診断とテストの後に、認証済みの実 HTTP でも確かめる。過去に、Apache の `Location` が `DirectoryMatch` の拒否を上書きしていた例がある。

## 3. ロールバック

まず対象を確認し、同じバックアップ ID で適用する。

```
sudo deploy/tet2-rollback.sh --backup-id=<バックアップID>
sudo deploy/tet2-rollback.sh --apply --backup-id=<バックアップID>
```

データベースまで戻す場合は、関連サービスと Web の書き込みを止め、オフラインを確認してから二重のフラグを付ける。

```
sudo deploy/tet2-rollback.sh --apply --backup-id=<バックアップID> --restore-db --db-offline-confirmed
```

ロールバック直前の状態もバックアップに保存される。配備前に存在しなかったファイルは削除せず、退避先へ移す。

## 4. 承認制の入力値収集の運用

この機能は既定で無効である。有効にする場合、次を守る。

- 暗号鍵は、Web の公開領域とリポジトリの外に、32 バイトのファイルとして置く。読めるのは PHP の実行者だけにする。鍵をソース、データベース、バックアップの記録に入れない。紛失すると本文は復号できなくなる。
- 鍵の場所は、Apache 版 PHP の `open_basedir` で許可する。
- 収集は、システム管理者が顧客の承認番号を登録したキャンペーンだけで、新しく生成する偽ログインページが本文を送る。既存の生成済みページは自動では変わらない。
- 収集した本文は暗号文としてのみ保存し、通常のレポートや CSV、Excel には載せない。閲覧はシステム管理者に限り、復号は監査を伴う。顧客の管理者には見せない。
- 統計を確定した後に「クローズ」で暗号化本文を消去できる。クローズ後は再収集と確定解除を拒否する。キャンペーンの削除時にも本文を消去する。
- データベースの行削除は、バックアップや WAL からの物理消去までは保証しない。バックアップの保持と鍵の管理は別途、運用として設計する。

反映後は、未認証のダミー POST がアプリ由来の 403 を返すこと、管理 API がログインへ転送されること、内部ディレクトリが 403 のままであることを、実 HTTP で確認する。

## 5. タイマーの管理

タイマーの一覧と周期は詳細設計書の第4章にある。運用上の注意は次のとおりである。

- 教育の割当（`tet2-edu-enroll`）と催促（`tet2-edu-reminder`）は既定で停止している。有効にすると実在の従業員へ教育メールが届く。明示の指示なしに有効化しない。
- 定期キャンペーン（`tet2-campaign-automation`）は下書きの生成だけを行い、配信は手動の起動を必要とする。配備しただけでは有効にせず、パイロットの承認後に別の工程で有効化する。
- 報告メールの取込（`tet2-report-ingest`）は5分ごとに動く。派生データを是正するときは、先に再取込の入口（取込のフィルタ）を本番へ入れる。順序が逆だと、5分ごとの取込が誤ったデータを戻してしまう。

## 6. 送信の緊急停止

配信を緊急に止める場合、対象キャンペーンのデータ保存先に停止フラグ（`stop_sending.flag`）を置く。フラグを検出したバッチは取り消され、キャンペーンは一時停止になる。

## 7. バックアップの保持

方針は、最新10世代かつ30日未満を保持する。配備は自動で古いバックアップを消さない。専用のコマンドも既定は確認だけで、物理削除せず退避先へ移す。

```
deploy/tet2-prune-backups.sh
sudo deploy/tet2-prune-backups.sh --apply
```

退避先の物理削除は、このコマンドの範囲外とし、別の承認済みの運用で行う。

## 8. リハーサルとテスト

一時ディレクトリだけで、配備、データベースのバックアップ、ロールバック、改ざんの拒否、バックアップの整理を検証する。

```
bash deploy/tests/deploy_rehearsal_test.sh
systemd-analyze verify deploy/systemd/*.service deploy/systemd/*.timer
```

アプリケーションのテストは、合成データベースと `.test` ドメインだけで行う。本番データベースや個人情報には依存させない。

```
bash web/tests/run.sh
python3 -m unittest discover -s bin/tests -p 'test_*.py'
```

## 9. 障害対応

- 送信が止まった場合: `tet2-worker.service` の稼働と、送信スケジュールの滞留、失敗バッチを確認する。必須の添付が欠けているとキャンペーンが一時停止する。
- 生成物と QR や添付の URL が合わない場合: ビーコンの基準（`beacon_base`）がデータベースの値で生成されているかを確認する。過去に、生成が古い設定ファイルを見ていた例がある。
- クリックや開封の誤検知: `open` はメールの開封ではなく偽サイト側のビーコンである。ボットなどの巡回を取込時に除外する。是正の前に、再取込の入口のフィルタを本番へ入れる。
- 派生データの是正は、再取込の入口を直してから行う（第5章）。
