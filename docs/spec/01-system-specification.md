# 01. システム仕様書

対象システム: TET v2（標的型メール訓練およびセキュリティ教育システム）
版: 2026-09-24 時点の実装（リポジトリ HEAD `9aafa33`）に基づく。
位置づけ: 本書は機能要件と非機能要件、入出力を定める。設計の詳細は基本設計書と詳細設計書、運用は運用手順書、画面操作は利用マニュアルに分ける。

## 1. システムの目的と範囲

TET v2 は、企業の従業員へ模擬的な標的型攻撃メールを送り、その反応を測定して、必要な従業員へセキュリティ教育を提供するためのシステムである。
複数の顧客組織を1つのシステムで扱うマルチテナント構成を採り、顧客ごとにデータを論理的に分離する。
旧版 v1（`/tet`）とは別に構築し、当面は両者を共存させる。本書は v2 だけを対象とする。

対象とする業務は次の4つである。

- 訓練メールの作成、配信、反応の測定。
- 測定結果の集計と、顧客への報告。
- 訓練の失敗傾向に基づくセキュリティ教育の管理。
- 従業員から寄せられた不審メールと、疑似フィッシングの報告メールの受付と確認。

## 2. 利用者と権限

利用者は、システムを操作する管理アカウントと、訓練や教育を受ける対象者に分かれる。

管理アカウント（`users` テーブル）は4つの役割を持つ。

- **superadmin**：全テナントを横断して操作する。テナントの作成と、全テナントを対象とする一部の集計を行う。
- **tenant_admin**：自テナントの管理者。
- **operator**：訓練の作成や配信など、データを変更する操作を行う。
- **viewer**：閲覧だけを行う。

対象者（`targets` テーブル）は、訓練の宛先であり、教育の受講者でもある。訓練対象者と受講者を別々に管理せず、`targets` に統合している。

権限の基本則は、参照（GET）は viewer 以上、変更（POST）は operator 以上に限り、変更操作には CSRF トークンを必須とすることである。認証情報の閲覧など一部の操作は、さらに強い権限に限定する（第3章9節）。

## 3. 機能要件

### 3.1 テナント管理

superadmin は、テナント（顧客組織）を作成し、名称と識別子（slug）、データ保存先（data_dir）、状態を管理する。
すべての業務データはいずれかのテナントに属し、テナントをまたいで参照できない。

### 3.2 管理アカウント管理

管理アカウントの作成、更新、削除、一覧を行う。
パスワードはハッシュとして保存する。ログインの失敗回数を数え、一定回数を超えたアカウントを一時的にロックする。

### 3.3 対象者とグループ、役職の管理

対象者について、作成、更新、削除、一覧、CSV による一括取込と書き出し、削除の取り消しを行う。
対象者は、氏名、メールアドレス、会社、部署、役職などの属性を持つ。削除は物理削除ではなく、削除日時（`archived_at`）を記録する論理削除とする。訓練の効果測定に影響しないテスト用の対象者は、フラグ（`is_test`）で区別する。

グループは、対象者をまとめて訓練の対象に指定するための単位である。作成、更新、削除、一覧、メンバーの追加と削除を行う。

役職マスタは、会社と役職の組み合わせを管理し、対象者へ一括で適用する。会社別、役職別の集計と、設定の網羅状況を確認できる。

### 3.4 テンプレート管理

訓練メールと教育で使う文面をテンプレートとして管理する。
テンプレートは、件名、本文、偽ログインページ、種明かしページ、eラーニングの5種類（`kind`）に分かれる。共有の雛形（`is_preset`）と、テナント固有のものがある。
作成、更新、削除、一覧、シナリオ単位の作成、CSV による取込と書き出しを行う。

### 3.5 訓練キャンペーンの作成と配信

キャンペーンは訓練の実施単位である。次の機能を持つ。

- 作成、更新、削除、複製、名称変更、一覧、取得。
- 下書きの段階的な編集（基本情報、対象者、シナリオ、日時と送信量、送信環境、最終確認の6手順）と、一覧編集への切替。どちらも同じ下書きを保存する。
- 配信前確認。対象人数、総通数、テスト転送先ごとの通数、開始できない理由を表示する。
- 起動、停止、下書きへの差し戻し、進捗の取得。
- 配信方式（`content_delivery`）の選択。既定は対象者へコンテンツを振り分け、全件配信では対象者とコンテンツの組み合わせごとに追跡できる。
- 送信量の制御（分割数、分割間隔、営業時間帯、営業日のみ）。
- 偽ログインページ、リンク、QR コード付き文書、添付ファイルの生成と、生成失敗の事前検出。
- テストキャンペーン。全送信行を指定したテスト宛先へ均等に転送する。テスト宛先が空のときは生成と配信を拒否し、本番宛先へは送らない。
- 送信後でも本番とテストの区別を切り替える操作。

配信前確認の後に設定、対象者、テンプレートが変わった場合、開始操作を拒否し、再確認を求める。

### 3.6 定期キャンペーン（半自動化）

月次や四半期などの規則から、レビュー用の下書きを自動で生成する。作成、更新、削除、一時停止、再開、プレビュー、即時生成を行う。
自動化は下書きの生成までにとどめ、実際の配信は手動の起動操作を必要とする。完了済みの均等割りキャンペーンをコンテンツの供給元として選ぶと、従業員ごとに前回とは別のコンテンツを割り当てられる。

### 3.7 レポートとログ

キャンペーンの反応を集計し、顧客への報告に用いる。

- サマリー、明細、キャンペーン別、偽サイトのビーコン別、個人別の集計。
- Excel への書き出し（サマリー、会社別、役職別、コンテンツ別、日別、訓練結果、訓練結果ログ、返信者の複数シート）。
- リスクの集計（会社別、個人別、再訓練の推奨）。
- 集計値の確定と解除、統計確定後のクローズ。

ログ管理では、配信ログ、イベント、送信スケジュール、監査ログ、実受信メール（Maildir）、Web アクセスログ、報告メールを一覧できる。各一覧は CSV と Excel へ書き出せる。Web アクセスログには、IP からの地域推定と逆引きを、負荷を避けるためキャッシュ表示と明示更新に分けて提供する。

### 3.8 リスクの評価

訓練で観測した行動（未開封、開封、クリック、認証情報の入力、返信）を重み付けし、直近の行動を重く見る時間減衰を加えて、人単位のリスクを評価する。
評価結果から、再訓練の推奨者と推奨する教育カテゴリを提示する。

### 3.9 承認制の入力値収集

偽ログインページで従業員が入力した値の扱いは、既定では行為の発生だけを記録し、入力された文字列は保存しない。
顧客の承認がある場合に限り、入力された本文（メールアドレスとパスワード）を保存できる。保存する本文は専用のテーブルに暗号化して格納し、システム管理者専用の操作でのみ復号して閲覧する。顧客の管理者には見せない。
入力本文は、通常の明細や CSV、Excel へは再表示しない。日数による自動削除は行わず、キャンペーンの削除時と、統計確定後のクローズ時に消去する。閲覧、承認、一覧の操作を提供する。

### 3.10 セキュリティ教育

訓練の失敗傾向に基づいて、教材と確認テストを配信する。

- 教材カテゴリの管理（作成、更新、削除、複製）。
- 教材の管理と、PowerPoint（`.pptx`）からのスライド取込。
- 確認テストの設問管理と、Excel（`.xlsx`）による一括取込、書き出し、テンプレート配布。
- 教育配信の作成、更新、削除、起動、催促。
- 受講（トークンによる受講開始と回答提出）。
- 教育レポート（全体、配信別、横断、推移）。

教育の割当と催促を自動化する処理は実装済みだが、実在の従業員へ教育メールを送るため、既定では停止している。有効化は運用手順書の手順に従う。

### 3.11 報告メールの受付

疑似フィッシングを正しく報告した従業員のメールを受け付け、対象のキャンペーンと照合する。
報告メールの一覧、照合結果の確定と却下、未照合の一覧を提供する。取込は定期的に実行する。

### 3.12 不審メールの解析

従業員から寄せられた不審メールを `.eml` 形式で受け付け、オフラインで解析する。
一覧、取得、アップロード、再解析、レピュテーション照会（VirusTotal）、更新を提供する。解析結果は履歴として残し、レピュテーションはキャッシュする。

## 4. 入出力

### 4.1 入力

- 管理者のブラウザ操作（API は `?action=` 形式、変更操作は CSRF トークンを伴う）。
- CSV による対象者とテンプレートの一括取込。
- PowerPoint による教材、Excel による設問の取込。
- 不審メールの `.eml` ファイル。
- 従業員から届く報告メールと実受信メール（Maildir）。
- 外部連携の API 呼び出し（Bearer 認証、重複実行を防ぐ idempotency キー）。

### 4.2 出力

- 訓練メール（SMTP でローカルの `localhost:25` へ送信）。
- 生成物（送信用 CSV、偽ログインページ、リンク、QR コード付き文書、添付ファイル）。
- 集計とログの画面表示、CSV、複数シートの Excel。
- 受講者向けの教材と確認テストの画面。

## 5. 非機能要件

### 5.1 マルチテナントのデータ分離

すべての業務テーブルはテナント識別子（`tenant_id`）を持ち、リポジトリ層（`Db::forTenant()`）を通してテナントの境界を保つ。テナントをまたぐ参照は、全テナントを対象とする一部の superadmin 機能に限る。

### 5.2 セキュリティ

- OWASP Top 10 に対する診断と修正を行っている（内部 URL の遮断、IP 単位のレート制限、内部パスの遮断、権限外参照の多重防御）。
- コンテンツセキュリティポリシーに対応するため、外部の配信網に依存せず、必要なライブラリをローカルに配置する。
- 変更操作には CSRF トークンを用い、出力はエスケープする。通信には時間制限を設ける。
- 入力値の収集は既定で行わず、収集する場合も暗号化と権限制限、消去規則を伴う（第3章9節）。

### 5.3 可用性と運用

- 送信処理は常駐サービス（`tet2-worker`）が担い、送信スケジュールを監視して配信する。
- 定期処理は systemd タイマーで実行する。教育の割当と催促は既定で停止している。
- 配信の緊急停止は、データ保存先に停止フラグ（`stop_sending.flag`）を置くことで行う。
- データベースは Web から到達できない場所に置き、WAL モードで運用する。データベースの実体、個人情報、ログはバージョン管理の対象外とする。

### 5.4 性能

- 送信量は分割数と分割間隔で制御し、営業日と営業時間帯に限定できる。
- Web アクセスログの地域推定は、同期処理による遅延を避けるためキャッシュ表示と明示更新に分ける。

## 6. 制約と前提

- 実在の従業員へメールを送る本番システムである。配信、データベースの変更、タイマーの有効化は、承認を得た手順でのみ行う。
- 旧版 v1 と共存し、送信本体（`send_email.py`）は v1 と共用する。
- フレームワークを採用せず、素の PHP 8.4 と素の Python 3.13 で構成する。
