# TET v2 プロダクトロードマップ

最終更新: 2026-08-08

本書は、現時点で未実装の機能候補と、実装を見送った判断の理由・再検討条件を記録する。
優先順位は、現在が一人運用であることを前提に、運用負荷の削減と訓練効果の向上を重視する。

## 判断記録

### 本番キャンペーンの四眼承認

- 状態: 保留（将来候補として残置）
- 判断日: 2026-08-08
- 理由: 現在の作業者が一人であり、申請者と承認者を分離できないため。現時点で導入すると、
  実質的な安全性を高めずに操作工程だけが増える。
- 現行方針: テストキャンペーン、送信前確認、送信制御、audit logを用いて一人運用を継続する。

次のいずれかが発生した時点で再検討する。

- 二人目のoperatorまたはtenant_adminが参加する
- 顧客テナント自身がキャンペーンを作成・実行する
- 誤配信時の影響範囲が拡大する
- ISMS、SOC 2、顧客契約などで職務分離が要求される

将来実装する場合は、自己承認禁止、テナント境界、申請後の編集による承認失効、
設定snapshot/hash、API側の承認検証、audit log記録を必須要件とする。

## 推奨バックログ

### P0: Git正本と本番の同期・安全なdeploy/rollback

`/root/tet2` はGit管理されているが、2026-07-25の初回commit以降に本番へ加えられた変更が
未反映である。機能追加より先に、本番差分を調査して正本へ取り込み、staging検証から本番配備までを
再現可能にする。

完了条件:

- 本番固有のsecret、DB、ログ、生成物を除外して差分を正本へ集約する
- deploy前のbackup、dry-run、配備対象一覧、rollback手順を用意する
- PHPテスト、Python構文検査、実HTTP smoke testを配備条件にする
- 本番ディレクトリでの直接編集を通常運用から外す

### P1: キャンペーン自動化

定期訓練の作成・対象選定・予約を自動化し、一人運用で最も時間を消費する反復作業を減らす。

候補機能:

- 毎月・四半期・任意間隔の繰り返しschedule
- 指定期間内での送信日時ランダム化
- 前回と異なるテンプレートやscenarioの自動選択
- group、部署、前回失敗者などによる対象条件
- 実行前にdraftを自動生成し、手動確認後に送信する半自動モード
- 自動生成・変更・実行をaudit logへ記録する

初期版は完全自動送信にせず、「draft自動生成 + 手動実行」とする。これにより、一人運用でも
誤設定を確認する余地を残しながら作業量を減らせる。

### P1: アクション中心のリスクダッシュボード

現在の件数中心のdashboardを、次に誰へ何をすべきか判断できる画面へ拡張する。

候補指標:

- 未開封、開封、クリック、認証入力、返信を重み付けしたrisk
- 直近の行動を重くする時間減衰
- 部署・group別の失敗率と推移
- 教育の未着手、期限超過、完了、score
- 再訓練推奨者と推奨教育category

初期版は永続的なrisk scoreを保存せず、既存eventsと教育結果からAPIで計算する。
計算規則を確認してからsnapshot化する。

### P1: リスク連動型の教育割当

キャンペーンで発生した行動に応じて教育内容を変える。

- 開封のみ: 基礎的な見分け方
- リンククリック: URL確認と誘導手法
- 認証情報入力: credential phishingとMFA
- 添付操作: malware・マクロ・ファイル共有
- 繰り返し失敗: 難易度を上げた再教育

実装前に、`EduAutoEnroll` が共有問題（`tenant_id IS NULL`）もfallback候補として取得できるようにし、
tenant固有問題との優先順位をテストで固定する。

### P2: 通知テンプレートとpositive reinforcement

教育招待・reminderのハードコード文面をテナント別テンプレートへ移し、previewと差し込み変数を提供する。
あわせて、疑似フィッシングを正しく報告した利用者へ即時に称賛・解説を返せるようにする。

最低限の通知種別:

- 教育割当
- 期限前reminder
- 期限超過
- 完了通知
- 疑似フィッシング報告へのpositive reinforcement

### P2: 失敗宛先だけの安全な再送

現在のworker失敗時はschedule全体がfailedになり、automatic retryを行わない。SMTPの一時障害などに限り、
未送信の宛先だけを再試行できるようにする。

重複送信を避けるため、recipient単位のidempotency、永続的なattempt記録、指数backoff、最大回数、
恒久エラーとの分離、手動停止を必須とする。初期版は自動再試行ではなく「安全に再送できる候補の表示」から始める。

### P2: 運用ヘルス画面と通知

一人運用では、利用者向け機能より先に異常の見逃しを減らす価値が高い。

- Apache、worker、timer、DB WAL、disk容量、backup世代の状態
- Cloudflare 521など外形監視の失敗
- scheduleの滞留、failed batch、教育通知失敗
- 画面上の警告と、必要に応じたメールまたはSlack通知

### P3: SSO/MFA・ディレクトリ同期

管理者が増えた段階で、OIDC SSOとMFAを優先する。Entra IDやGoogle Workspaceからの利用者・group同期は、
手動CSV管理の負荷が顕在化した段階で別projectとして設計する。外部IdP設定、secret管理、退職者無効化、
同期失敗時の扱いを含むため、他機能と分離して実施する。
